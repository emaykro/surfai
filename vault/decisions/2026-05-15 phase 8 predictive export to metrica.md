# Phase 8 — Predictive Export to Metrica

**Date:** 2026-05-15
**Status:** Accepted, implementation in progress.

## Context

Phase 7 (per-site fine-tuned CatBoost) is live and stable. ~80% of new sessions are scored every 5 min, calibration is solid (ECE→0), ym_uid coverage is ~86%. The Metrica push pipeline (Phase 6.5/4A) and the Metrica import pipeline (4B) both work end-to-end for stefcom.

The ML score is currently only consumed internally — by the dashboard. The ad platforms (Yandex Direct in particular) cannot use it. Smart Bidding strategies optimize toward offline conversion goals; if we feed Direct only *real* leads we lose volume signal and wait days for the platform to learn.

## Decision

Push high-confidence ML predictions to Metrica as a **separate offline conversion goal** called `predicted_lead`, so Yandex Direct Smart Bidding has a fast, high-volume training signal alongside real leads.

We will **not** start with real-time visit params (`ym('params', ...)`) or GA4 user_properties:
- All 7 production sites use Metrica, none use GA4 → 8c is pure cost
- Real-time params (8b) require new server endpoint + SDK changes + Metrica integration on the client. 8a reuses the existing push pipeline. Same business effect at a fraction of the work. 8b can come later as an enhancement.

## Design

### What gets pushed
A SURFAI goal `lead_predicted` (type=`backend_api`, project=Luch). Conversions of this goal are auto-generated by a new worker `score-predicted-leads.js` when:
1. A session has `model_prediction_score >= THRESHOLD` (default **0.7**, conservative).
2. The session is "settled" — last event ≥ 15 min ago. Prevents pushing on partial scores that may still change as the user interacts more.
3. No `lead_predicted` conversion already exists for that `session_id` (per-session dedup).

### Push to Metrica
Reuses `metrica-conversions.js`. Two small changes required:
1. The goal pattern `g.name ILIKE 'lead%'` already matches `lead_predicted` — no change needed there.
2. The script currently sends `Target=FALLBACK_TARGET` (always `lead`) for every counter. We need per-goal Metrica target name so `lead_predicted` is sent as `predicted_lead`, not as `lead` — otherwise we'd poison the real-lead signal.

Adding `goals.metrica_target_name TEXT` (nullable). If NULL → fall back to the env default (current behavior); if set → use it as the CSV Target.

For `lead_predicted` we'll set `metrica_target_name = 'predicted_lead'`. Existing `lead_*` goals stay NULL → they keep sending `Target=lead`.

### Counter-side prerequisite (operator task)
Each of the 7 Metrica counters needs an **offline-conversion goal** named `predicted_lead` configured in the Metrica admin. Without this Metrica returns API_ERROR for the upload.

### ML training feedback loop
**Risk:** if we train ML on conversions that include `lead_predicted`, the model trains on its own output → score inflation → more `lead_predicted` → reinforcing loop. ML training must filter to **real** conversion goals only.

Mitigation: `ml/data/load.py` (or equivalent loader) must exclude `lead_predicted` from the label set. Concretely: `WHERE goal_name NOT IN ('lead_predicted')` or equivalent flag. Added to the implementation checklist.

### Threshold
Start at **0.7** — high precision, lower recall. We'd rather under-volume Yandex Direct than train it on noisy positives.
After 2 weeks of observation we re-evaluate per-site. Tracking metric: real-conversion rate among `lead_predicted` sessions (precision@0.7). If precision > 50% we can lower threshold; if < 30% we raise it.

Per-site threshold override: deferred. If needed, add `sites.predicted_lead_threshold DOUBLE PRECISION` later.

### Cadence
Worker runs every 10 min (timer). Looks back 24 h for "settled" sessions to catch any that just crossed the 15-min staleness gate.

## Alternatives Considered

**Push every score, no staleness gate.** Rejected — sessions can have wildly different scores at different points (early in session vs after deep scroll). Pushing early would create duplicate predicted_leads for the same session at different intent levels. The staleness gate gives one stable score per session.

**Use `lead` as Target for predicted as well.** Rejected — poisons the real lead signal in Yandex Direct's optimization. The whole point of `predicted_lead` is that it's *distinct* from a confirmed lead.

**Push to GA4 instead.** Rejected — none of our 7 prod sites use GA4. Would be infrastructure for no consumer.

**Real-time visit params via `ym('params', ...)`.** Deferred to Phase 8.1. Useful for ad hoc Metrica segmentation but not for ad bidding (Smart Bidding optimizes on goals, not params). The current goal-based path is the higher-ROI starting point.

## Open Questions

- Per-site threshold override — wait until we have precision/recall numbers.
- Backfill historical sessions or start fresh from launch? Decision: **start fresh**. Backfill would create a huge initial pulse to Yandex Direct that does not reflect the steady state.
- Should `lead_predicted` conversions also be visible on the dashboard `/api/sessions/:id/conversions` endpoint? Yes — they're real rows in `conversions`, no filter needed.
